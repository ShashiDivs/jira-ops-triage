# Public demo: put the app on a URL, show it, take it down

For a supervised session, not a permanent service. The whole app (React page + API, one container) and a
throwaway Postgres run in Azure Container Apps, in **one resource group** that `down` deletes in one go. The
Foundry project, the four hosted agents and the container registry are never touched.

```
 audience  --https-->  ops-demo-app  (React + API, passcode-gated, ticket-capped)
                           |  internal only
                           +-->  ops-demo-db  (pgvector Postgres, no disk, no internet address)
                           +-->  models in Foundry   (keyless: the app's managed identity)
```

Everything is `cd backend && python -m hosted.demo ...`. Each step shows its command, cost and undo, and does
nothing unless you type `y`. There is no run-everything mode.

## Before the day (about an hour, once)

1. **Choose a passcode** and put it in your own, gitignored `.env`: `DEMO_DEPLOY_PASSCODE=...` (8+ characters).
   The tool never generates, prints or logs it. Share it only with the people who should get in.
2. **Commit your work first.** The image is tagged with the git commit; a dirty tree produces a `-dirty` tag.
3. `python -m hosted.demo plan` and read it. Add `--cap N` / `--rate N` to change the limits (default: 30
   tickets in total, 5 per minute per client) and `--hosted-specialists` to also let the app call the four hosted
   agents (needs a broad role, see below).
4. **Rehearse the whole thing once, then run `down`.** The commands follow the CLI's `--help` but had not been run
   against live Azure when written, so expect to fix something on the first pass.

## Up (in this order; each is `python -m hosted.demo apply --step <key>`)

`register_app_provider` (once per subscription) -> `create_resource_group` -> `create_identity` ->
`grant_registry_pull` -> `grant_model_access` -> `build_image` -> `import_postgres_image` ->
`create_environment` -> `create_database_app` -> `create_web_app` -> `smoke_test`

`smoke_test` waits for the app (the first start migrates and seeds, so allow a few minutes) and prints
`PUBLIC URL: https://...`. It checks that the page loads and that the API refuses a call without the passcode;
it does not use your passcode. Role grants can take a few minutes to take effect, so if `create_*_app` fails on
the image pull right after `grant_registry_pull`, wait and retry.

## During

Open the URL, enter the passcode, then follow "Try it" in the README. Keep the Foundry portal open in another tab
to show the four hosted agents. `python -m hosted.demo status` shows what exists and the URL.
If something misbehaves: `az containerapp logs show --name ops-demo-app --resource-group ops-triage-demo --tail 80`.

## Down

`python -m hosted.demo down` lists what it will delete, asks once, removes the demo identity's role assignments,
then deletes the resource group and waits until it is gone. It refuses any group that is not tagged
`purpose=temporary-demo`. Two images stay in the registry (cents a month); `az acr repository delete` removes them.

## What it costs (list prices, swedencentral; check your own billing)

Both containers run all the time at 1.5 vCPU / 3 GiB in total: about **$0.16/hour fully active, $0.05/hour idle**,
so roughly **$1-4 for a working day**. Add the model calls the tickets make (the 30-ticket cap bounds this to a few
dollars at most), the Log Analytics ingestion (a few MB) and the registry storage. Nothing bills after `down`
except the registry images.

## What protects it, and what does not

- A shared passcode gates the API; the page itself is public but contains no data. A cap of N tickets in total and
  a per-client rate limit bound the spend; the scheduler is off.
- It is **not** user accounts: anyone with the passcode can type `bob` in "Approving as" and approve a security
  ticket. Share the passcode only with the audience.
- The database has no internet address and no disk; its password is generated by the tool, never printed, and kept
  only as a Container Apps secret. A restart of the database loses pending approvals.

## Not verified until run

`az containerapp` argument details; that an ABAC registry accepts `az acr import`; that Container Apps can reach the
database by its internal TCP address; that the identity's role grants take effect before the first image pull;
and, with `--hosted-specialists`, that a managed identity can invoke the hosted agents (if not, the app falls back
to calling the models directly and the demo still works).
